# Data fetcher

For `apps/data-fetcher` and `libs/data-fetcher`. The tables it writes are in CLAUDE.md's Server conventions; what the data means is in `features.md`.

- **One run, then exit:** `apps/data-fetcher/src/main.ts` boots a Nest standalone context (no HTTP), refuses to go on while migrations are pending (only frontend-api migrates), runs every fetcher in order, `teams` → `players` → `standings` → `games` (the players and the games need the teams), closes and exits 1 if any failed. A failed fetcher doesn't stop the ones after it. The schedule lives outside the code (Cloud Scheduler → Cloud Run Job in production, `pnpm nx run data-fetcher:run` locally), so a crash never leaves a stuck process.
- **Runs from its sources** (`node -r ts-node/register`, `.env` loaded with `--env-file-if-exists`): no bundle until it's deployed (`docs/backlog.md`).
- **The provider is API Ninjas** (`https://api.api-ninjas.com/v1`, the key in `X-Api-Key`, always `league=nba`), called only by `ApiNinjasClient` (`libs/data-fetcher/api-ninjas-client`): a method per request, its answer mapped to our create objects (`mappers.ts`), so the fetchers see only our types. Its response types (`api-ninjas.types.ts`) are checked against real responses (`fixtures.ts`). The tables' NOT NULLs, enums and foreign keys refuse what's missing or unknown; **a key can be missing instead of null** (`college`): map it to null. A refused call throws `ApiNinjasError` with its `status` (400 for a bad key, 429 for the quota). No retries: the next run redoes what failed.
- **The fetchers** (`libs/data-fetcher/fetchers`, a `*-fetcher.service.ts` each, `run()`):
  - `teams-fetcher`: `basketballteams`, one request; upserts every team. Teams are never deleted (everything points at them).
  - `players-fetcher`: `basketballplayers?team=<id>`, one request per active team (30), one at a time, then all in one transaction (`TeamPlayerDalService.replaceRosters`): the players upserted on their teams, anyone else on a team released (`team_id` null; players are never deleted, their days stay), and today's `team_players` replaced by what this run saw. Writes nothing unless every roster came back non-empty (a missing one would release its team).
  - `standings-fetcher`: `basketballstandings`, one request, the current season's, in one transaction (`StandingHistoryDalService.recordStandings`): `standings` upserted to the latest, and today's row per team upserted in `standings_history` (a second run that day updates it).
  - `games-fetcher`: the task pool, over the season (`SEASON_ID`, default: the newest in `seasons`). Its days: **the scores to update**, every day from the last one with a scored game (`GameDalService.lastScoredDate`; the season's start if none) to today, and **the days with no games** (`datesWithGames`), the rest of the schedule. Nearest to today first, one request per day (`basketballgames?date=`), one at a time, up to `GAMES_MAX_REQUESTS` (default 50); the next run picks up the rest. A future day that has its schedule isn't fetched again until its scores are due. A 429 stops the pool without failing the run; another failure skips the day and fails the run at the end.
- **"Today"** is the league's day, US Eastern (`easternDate()` in `days.ts`), for `team_players.date` and the games' days. Fetchers take it as `run(today)`, so specs pass their own.
- **The quota decides the schedule:** the free plan is 3,000 calls a month and 100 an hour, the current season only, no live scores. A run is 32 calls (1 + 30 + 1) plus up to `GAMES_MAX_REQUESTS`: keep the sum under 100 an hour, and daily runs under 3,000 a month. Days without games (Thanksgiving, the All-Star break) are asked for again every run.
- **Logs:** a line per fetcher (what it wrote) and per run of each (`<name> done in <ms>`); the games pool says how many days it had, fetched, failed and left. A failure is an error line with its stack. Never the key.
- **Tests** (`fetchers.spec.ts`): the real client and fetchers against the test DB, with only `fetch` faked, answering with `fixtures.ts`'s real responses (`answerWith(url => ...)`); a test changes the answers to make a trade, a quota or a failure. The client's own spec checks the requests and the mapping. Never call the real provider from a test.
- Env: `API_NINJAS_KEY` (required: the run fails at boot without it; put it in `.env`, see `.env.example`), `SEASON_ID`, `GAMES_MAX_REQUESTS`, plus the `DB_*` from CLAUDE.md's Database. Never commit the key or log it; the Postman collection holds one, so keep it out of the repo.
